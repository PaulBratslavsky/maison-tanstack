# Handoff: build Maison on TanStack

For the agent that starts this project. Read this file, then `docs/spec.md`, then skim both files in `docs/reference/`. Then start with "Your first steps" below.

## What you are building

A new, separate project at `~/work/maison-tanstack`. It rebuilds the Maison demo (`~/work/maison-demo`) feature for feature:

- the customer app with **TanStack Start** (Router, Query, Form) in place of Next.js;
- **TanStack AI** for every model call: the concierge in the app (server and browser), and the staff assistant and inquiry labelling in Strapi;
- **Strapi 5** as the back end, with a fresh Maison plugin and Strapi's MCP server.

Paul Bratslavsky owns it. He wants it to read as a clean example of Strapi + TanStack Start + TanStack AI + MCP.

## Rules that are not negotiable

These are also in `CLAUDE.md`.

- **Never change `~/work/maison-demo`.** Read it and port code from it. Don't commit, push, install or run its scripts. Its `main` deploys to Paul's production LINE app.
- **Never print, paste or commit a secret:** a value from any `.env` file, a token, a password, an API key. Read variable names only. Generated secrets go straight into `.env` files that are git-ignored and `chmod 600`.
- **Credentials.** Local mode needs no LINE credentials. The Anthropic key is already in place (see "State at handoff"). Ask Paul before copying any other credential.
- **The local Strapi admin password** is generated by `init-env` into `strapi/.env`. Never print it. Paul reads it there.
- **No remote, no push, no deploy** without Paul's explicit OK. Ask before creating a GitHub repository.
- **Writing rules** for every UI string, comment, doc and commit message: plain English, short sentences, no em dashes, no en dashes, no metaphors or analogies. Name things literally.
- **Commits:** small, one logical change each, pathspec commits (`git commit -- <paths>`). Messages in the form `area: what changed, in plain words`, ending with `Co-Authored-By: <the model you run as> <noreply@anthropic.com>`.
- **Models in the product:** Sonnet for model features (Claude Sonnet 5.5, `claude-sonnet-5-5`), Claude Haiku 4.5 (`claude-haiku-4-5-20251001`) for inquiry labelling. Opus is overkill for the product.
- **Models for the work:** subagents that implement or review run on Sonnet. Only the final whole-project review runs on the most capable model.
- **Model calls only through TanStack AI.** Never a raw `fetch` to a provider, and no Vercel AI SDK.
- **Verify facts** about Strapi, TanStack and LINE against the installed source or the official docs before you rely on them, and name the page or file.
- **No Docker and no local Postgres.** Local development is SQLite.
- **By-hand checks that could message a real phone** use the made-up demo customers (`line:Udec0de...01` to `...05`), never Paul's own LINE.

## How to work

- Paul's process is subagent-driven development: a plan with tasks, a Sonnet implementer per task that writes the test first, runs every check and commits, then a Sonnet review, one fix round and a short re-review. Record each decision in a ledger as `Ruling: <what> - <why> - <cost if wrong>`. If the superpowers plugin is installed, use its `writing-plans`, `subagent-driven-development` and `finishing-a-development-branch` skills.
- Keep it lean. Paul said the original process was too slow: batch small fixes, review once per meaningful change, and don't wait on Paul between tasks unless a decision is his.
- Ask Paul only for decisions that are his (the spec's section 11 lists the defaults he can change). Otherwise pick the sensible default, note it in the ledger, and continue.
- Keep a progress ledger at `docs/progress.md` (committed), so the next session can pick up.
- Run the dev servers in a terminal tab Paul can see, and stop them while many files change.
